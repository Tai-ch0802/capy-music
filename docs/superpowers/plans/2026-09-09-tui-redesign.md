# capy 互動式介面重新設計

依 2026-09-09 的討論定案:**訊息流 + 彈出選單**(Claude Code 形態)、底部三行、打字加斜線選單、子命令的挑選器一起補。

---

## 1. 為什麼要重做(現況的四個問題)

實測 `View()` 在 80 欄下是 **19 行**,其中 8 行是水豚。

| 問題 | 成因 |
|---|---|
| 水豚頭重複三次 | inline 模式每 350 毫秒覆寫 19 行;視窗放不下時游標上移被頂端截斷,舊畫面留在上面 |
| 歷程完全不可讀 | 子命令的輸出寫進捲動區,TUI 也在同一個捲動區反覆重繪,兩者交錯 |
| 「不是選單」 | 現在只是把 shell 換個殼,要打字輸入子命令 |
| 進度條那行剛好等於終端機寬度 | 某些終端機寫滿最後一欄會多換一行,讓行數再差一 |

核心錯誤是**重繪面積**。把 TUI 管理的區域從 19 行降到 3 行,前兩個問題自然消失。

## 2. 畫面

### 2.1 啟動

水豚動兩秒(眨眼、嚼草)後**定格,印進捲動區**,之後永不重繪。

```
    __            __
   /  \__________/  \
  |   O          O   |
  |      ______      |
  |     (__..__)~~~~~~~~~
   \________________/

  capy · spotify · 打 / 看命令,? 看按鍵
```

### 2.2 一般狀態

```
[捲動區:永久,可往回捲、可複製]

  › pl list
  ID                名稱              曲數
  p.b16G4rbSY0DzME  日本都會之聲      -
  p.JL68l7EhogEeXd  冬日暖調          -

  › pl sync 冬日暖調
  DIR   ACTION  PROVIDER  POS  ...
  推送以上 3 筆變更到平台? [y/N] y
  已推送 3 筆變更

[TUI 管理區:只有這三行重繪]
────────────────────────────────────────────────
  ▶ 派對動物 · 1:23 / 4:09 · MacBook Pro
  › _
  space 播放/暫停 · ←→ ±10 秒 · / 命令 · ? 按鍵 · q 離開
```

### 2.3 斜線選單開啟

選單向上長,壓在捲動區前面(不是插進歷程)。

```
  ┌ 命令 ───────────────────────────────┐
  │ ▸ pl list      列出播放清單         │
  │   pl show      看清單內容           │
  │   pl sync      雙向同步             │
  │   search       搜尋曲目             │
  │   doctor       診斷設定與連線       │
  └─────────────────────────────────────┘
  ▶ 派對動物 · 1:23 / 4:09
  › /pl s_
  ↑↓ 選 · ⏎ 帶進輸入行 · Esc 收起
```

打字即時過濾。⏎ 把命令**帶進輸入行**(不直接執行),你可以再補參數。

## 3. 鍵位

| 鍵 | 一般 | 輸入中 | 選單開啟 |
|---|---|---|---|
| 打字 | ~~進入輸入~~ 見下 | 輸入 | 過濾 |
| `/` | 開命令選單 | 輸入 `/` | - |
| `?` | 展開完整鍵位 | - | - |
| `⏎` | - | 執行 | 帶進輸入行 |
| `Esc` | - | 清空輸入 | 收起選單 |
| `↑↓` | 翻歷史命令 | 翻歷史命令 | 選擇 |
| `space` | 播放/暫停 | 輸入空白 | - |
| `n` `p` | 上下首 | 輸入字元 | - |
| `←→` | ±10 秒 | 移動游標 | - |
| `+` `-` | 音量 ±5 | 輸入字元 | - |
| `r` | 重新連上(停擺時) | - | - |
| `q` | 離開 | - | - |
| `Ctrl-C` | 離開 | 離開 | 收起選單 |

**歷史命令**是新的:↑↓ 翻你這次 session 打過的命令。

**「打字直接進入輸入」沒有實作**(2026-09-09,PR 2):它和同一張表裡的熱鍵互相打架。最常打的命令
`pl …` / `play` / `pause` / `prev` / `push` / `pull` 開頭都是 `p`,而 `p` 是「上一首」——打 `pl sync`
會先跳一首歌,再把 `l sync` 丟進輸入行。靜靜改動播放狀態是最不能接受的一種意外,所以進輸入一律走 `/`。
熱鍵留著:少了它,這就只是一個換了殼的 shell。第 3 版的斜線選單本來就是 `pl …` 的正規入口(§2.3)。

**分隔線與提示符改成純 ASCII**(同上):`─`(U+2500)與 `›` 都是 East Asian Ambiguous,在 CJK 終端機
是兩欄。滿版的分隔線會直接翻倍成兩行;而 `textinput` 會把輸入行填滿到它自己算的 `w-1`,`›` 多佔的
那一欄剛好讓它寫滿最後一欄——正是 §1 第四列那個問題。

## 4. 命令執行的流程

1. 使用者按 ⏎
2. `tea.Println("› " + 原始輸入)` 把回音推進捲動區
3. `tea.ExecProcess` 跑 `capy <args>`,TUI 讓出終端機
4. 子命令的表格、`huh` 確認提示、`play` 挑選器全部原樣運作
5. 回來後,失敗才 `tea.Println` 一行 `✗ 結束碼 N`;成功不印(輸出本身就是證據)
6. TUI 在底部重畫三行

`--provider` 沿用現在的做法:使用者明指時帶給吃這個參數的子命令。

## 5. 錯誤與狀態列

你遇到的 `osascript 失敗(Music.app 未安裝或未授權自動化?)` 現在會一直佔著畫面。改成:

- **第一次發生**:`tea.Println` 一行進捲動區(永久記錄,可以回頭看)
- **狀態列**:只顯示 `▶ 讀不到播放狀態(r 重試)`,不重複整段錯誤
- **連續五次**:停止輪詢,不再每兩秒打一次 API;狀態列改成 `▶ 已停止輪詢(r 重試)`
- 命令列在任何情況下都能用,可以直接打 `doctor` 或 `auth login apple`

沒有播放內容時狀態列是 `▶ 沒有播放內容`,不佔額外行數。

## 6. 子命令要補的挑選器

原則:**不帶參數 + 在終端機 → 開挑選器;非 TTY 一律維持現在的錯誤**(可腳本化是硬約束)。

| 命令 | 現在 | 改成 | 選什麼 |
|---|---|---|---|
| `pl show` | `ExactArgs(1)`,不帶就錯 | 不帶參數開挑選器 | 平台清單(`ListPlaylists`) |
| `pl sync` | 不帶且沒 `--all` 就錯 | 同上 | 已連結的 canonical 清單(`pullTargets`) |
| `pl pull` | 同上 | 同上 | 同上 |
| `pl push` | 同上 | 同上 | 同上 |
| `pl unlink` | `ExactArgs(2)` | 兩段挑選:先選清單、再選平台 | canonical 清單 → 它的 links |
| `pl link` | `ExactArgs(2)` | 三段挑選(見下) | canonical 清單(可建新)→ 平台 → 該平台的清單 |
| `search` | 至少一個參數 | 不改(在 TUI 裡打 `search 五月天` 很自然) | - |

實作上抽一個共用的 `pickOne(title, items)`,從現有的 `runPlayPicker`(`play_resolve.go`)長出來,各處共用。

### `pl link` 的三段互動

它是唯一需要三段的,因為第一段可以是**還不存在的**名字(`pl link` 本來就會建立新的 canonical 清單)。

```
› pl link

┌ 要連結哪個清單? ─────────────┐
│ ▸ 通勤        已連 spotify    │
│   健身                        │
│   ─────────────────────────   │
│   + 建立新的清單               │   ← 選這個才跳輸入框
└───────────────────────────────┘

┌ 連到哪個平台? ───────────────┐
│ ▸ spotify                     │
│   apple                       │
│   local                       │
└───────────────────────────────┘

┌ 選 spotify 上的清單 ─────────┐
│ ▸ 日本都會之聲                │
│   冬日暖調                    │
└───────────────────────────────┘

已連結:通勤 → spotify:p.b16G4rbSY0DzME
```

**實作時順序對調成「平台 → 該平台的清單 → canonical 清單」**(2026-09-09,PR 1):現有的 `pl link` 是先驗證平台那半邊(在不在 `ListPlaylists` 裡、`GetPlaylistItems` 有沒有被 restricted)才進 `withCanonical`,canonical 先挑就得把平台的 API 呼叫搬進鎖裡、或多做一次 Drive FETCH。互動內容與可取消性不變,只是問的順序。第三段的標籤會標出「這個平台清單已經被哪個 canonical 佔走」,不讓使用者選完才被擋。

- 平台那段**列全部三個**,不先探測誰有登入:探測要建 provider 又慢,而選到沒登入的平台時錯誤訊息本來就指路 `auth login`。
- 已連結的組合會標注,選下去是重新連結(維持現在的覆蓋行為)。
- 中途 `Esc` / `Ctrl-C` 取消,不寫入任何東西。
- `pl unlink` 是兩段(選清單 → 選它已連的平台)。

## 8. 我自己決定的細節(有意見就說)

- 水豚動 **2 秒**後定格。不是「動到第一個命令」,因為那會讓重繪持續到不確定的時間點。
- 成功的命令**不印額外訊息**,只有失敗印 `✗ 結束碼 N`。輸出本身就是證據,多一行是雜訊。
- 選單**向上長**,最多顯示 8 筆,超過捲動。
- 命令歷史只存在記憶體,離開就沒了。存檔是另一個決定(要考慮寫哪、要不要清)。
- 底部區與捲動區之間畫一條 `────` 分隔線,讓「哪些會變、哪些不會」一眼看得出來。

## 9. Antigravity CLI 的比對(2026-09-09 查證)

依 [官方 features 文件](https://antigravity.google/docs/cli/features/),它的介面特徵是:固定的 prompt box、對話在上方捲動、可自訂的 status line(`/statusline`)、斜線命令直接打進輸入框並有自動完成、快捷鍵做「跳到下一個待處理」(Ctrl+J)與「立即批准」(Ctrl+K)。

**四項核心特徵與本設計一致**:固定輸入框、上方捲動歷程、斜線命令、狀態列。

它有而我們不採用的兩件,以及理由:

| 它的做法 | 為什麼 capy 不做 |
|---|---|
| 通知出現在 prompt box 正上方(fast path alerts) | 那是為「背景 subagent 需要批准」設計的。capy 沒有背景作業,需要決策的地方都在子命令的 `huh` 確認提示裡,沒有對應場景 |
| 選了項目後開全螢幕細節檢視 | 對應到 capy 是「`pl show` 三百首會洗版」。但終端機自身的捲動就是 pager;真的被洗版再考慮 |

`/statusline` 那種「狀態列可自訂」是之後的事,不進第一版。
