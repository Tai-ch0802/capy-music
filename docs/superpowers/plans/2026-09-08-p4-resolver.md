## §1 本次拍板的決策(2026-09-08;附錄 C 決策 19–25)

### 決策 19:觀測 cid 的身分規則改為三段式,base 也過同一個函式

P3 的 cid 純由觀測決定(`i:<ISRC>` 或 `p:<provider>:<id>`)。跨 ISRC 的 mapping(fuzzy 配對、人工釘選)一旦存在,純觀測的 cid 會與 canonical 的 cid 分裂:cid `i:A` 釘了 `apple:X`,而 Apple 回報 X 的 ISRC 是 B,下次 pull Apple 會算出 `i:B`,同一首歌變兩筆。

**新規則(spec §5.1 / §6.5.1 第 1、3 點)**:平台**現況 L** 觀測到的 (provider, id, isrc) 依序決定 cid:
1. `tracks.json` 裡已有 mapping `(provider, id)` → 該 cid(pinned 或不 pinned 都算);
2. 正規化 ISRC 在某個 track 的 alias set(`isrc[]`)→ 該 cid;多命中時取字典序最小的 cid 並在 stderr 警告(理論上不會發生,見下一段的不變量);
3. 否則 §6.2 公式;
4. 結果若是 `merged` 表裡的敗者 cid → 沿 tombstone 追到勝者(決策 21)。

**alias set 何時成長(PR #24 review 第 3 則)**:只在**人工操作**(review accept、`resolve pin`、合併)時成長,而且要過所有權檢查——候選的 ISRC 已屬於另一個 cid 就視同「候選已屬另一 cid」進 review,不靜默加入。`Observe` 與自動 mapping(`isrc` / `fuzzy`)**永不改動 alias set**:`isrc` 反查本來就同 ISRC 沒東西可加;fuzzy ≥85 若把候選的 ISRC 併進來,等於讓 85 分的判斷擴散到其他 provider 的觀測。代價:`p:` cid fuzzy 對到帶 ISRC 的曲目後,第三個 provider 觀測到那個 ISRC 仍會開新 cid,要人再合併一次——這是「分裂一次、人裁一次」而不是「靜默擴散」,fuzzy 只影響 ~1% 曲目,接受。由此得到的不變量:**每個 ISRC 至多屬於一個 cid**(T2b 性質測試:隨機操作序列後 `isrc → cid` 反查索引沒有一對多,且 `Identity` 兩次呼叫同解)。

**base 快照的重導只走 tombstone**:DERIVE 計數移除前,base 裡的每個 cid 只查 `merged` 表(沿鏈追到勝者);**不在表裡就保留快照原本的 cid,絕不落 §6.2 公式、也不查 mapping**。base 沒有 ISRC(`Snapshot` 只有 `Items` / `CIDs`),落公式會把 `(prov, id, "")` 算成不存在的 `p:` cid,移除計數歸零、永遠刪不掉——正是這條規則要防的孤兒(review 第 1 則的兩個情境:合併時敗者 id 只進 `conflicts[]`;cid 被釘到別的 id 而平台清單裡是另一個 id)。查 mapping 也不對:人把 id 從 X 改釘給 Y(髒 ISRC 的拆分),base 記的 (id, X) 若被重導成 Y,X 就再也對不到「base 有、L 沒有」而留成孤兒;保留原 cid X 才會在下次 pull 正確地「移除 X、新增 Y」。base 要問的是「這個舊 cid 現在叫什麼」,tombstone 正好回答這個問題,mapping 回答的是另一個問題。**不把 ISRC 加進 `Snapshot`**:tombstone 規則下 base 不需要 ISRC,沒有讀者的欄位不加(P3 對 `mappings` 三欄的同一標準)。

給定 `tracks.json`,以上全部決定性;所有裝置 FETCH 之後同一份 `tracks.json`,同解。R-6 與 T2b 的性質測試要涵蓋 review 第 1 則的兩個 miss 情境,不能只測 mappings 有聯集的樂觀路徑。

代價(進 P5 重審清單):item 的 cid 現在依賴觀測當下的 `tracks.json`,`tracks.json` 是共享檔、Drive 沒有 CAS,兩台裝置同時寫的 last-write-wins 可能讓同一錄音在兩台裝置算出不同 cid。P3 接受單裝置 LWW,這是它的新面向,不是新的解。

### 決策 20:mapping 物件化;schema 硬切換到 2

`tracks.json` 的 `mappings` 從 `{ provider: id }` 改為 `{ provider: { id, confidence, pinned, source, updated_at } }`:
- `confidence` 用 **0–100 整數**(不用浮點:`canon.Encode` 要逐位元決定性,整數沒有格式化歧義);觀測 100、ISRC 反查 95、fuzzy 60–84 進 review / ≥85 自動寫入、人工 100。
- `source` ∈ `observed | isrc | fuzzy | review`;`pinned` 只有 `review` 會是 true。
- 「這個平台沒有這首」= `pinned: true, id: ""`(不可得也是使用者意圖,要跟著 Drive 走,否則每次都重問)。
- **優先序**:pinned > observed > isrc / fuzzy。觀測到真實 id 會覆寫非 pinned 的自動 mapping;自動程序永不覆寫 pinned。
- **`updated_at` 只在 `(id, confidence, pinned, source)` 其中之一真的改變時才更新**(review 第 5 則):沒有實質變化的觀測不動 mapping 的任何欄位,否則每次 `pl pull` 都會因位元組不同而重傳整份 `tracks.json`(`commitCanonical` 是逐位元組比對)。比較兩個 mapping 是否等價時**不看 `updated_at`**(兩台裝置各自算出同一結果不該互相 LWW 覆蓋)。T2a 測試:連續兩次 pull、平台無變化 → `tracks.json` 位元組完全相同。
- `SchemaVersion` 是所有檔共用的常數 → 1 變 2 會讓**每一種檔**都變 2:v0.1.0 的 binary 對 schema 2 的 appdata 一律 `ErrSchemaTooNew` 拒寫,訊息已經是「請先 capy update」。這是**硬切換**:P4 的 release notes 要寫「每台裝置都要更新」。讀取相容:mapping 值是字串(舊形)照樣解(視為 observed / 100 / 不 pinned),寫出永遠是物件。**目前 Drive 上沒有任何真資料**(維護者的 appdata 為空),切換成本實際是零,但規則要寫下來。
- SQLite `user_version` 3 → 4:`mappings` 加 `confidence INTEGER, pinned INTEGER, source TEXT, updated_at INTEGER`;舊檔照 T9 規則保留為 `state.db.v3`。

### 決策 21:cid 合併只由人裁決,勝者決定性

- 「同一錄音、兩個 cid」(alias 收斂,spec §5.2 第一列)**只**在人工 accept / `resolve pin` 時發生;≥85 的自動寫入**絕不合併**:最佳候選 `(provider, id)` 已屬於另一個 cid 時,不論分數一律進 review,並在 review 裡把那個 cid 的證據(標題、時長、ISRC)一起列出。
- 勝者 = **字典序較小的 cid**(兩台裝置各自合併同一對也會得到同一結果),不是「正在 review 的那個」。敗者的 items 全部改寫成勝者 cid、alias set 聯集、mappings 聯集、`conflicts[]` 聯集,**敗者從 `tracks` 移除但在 `tracks.json` 的 `merged` 表留 tombstone `{敗者 cid: 勝者 cid}`**(SQLite `merged` 表鏡像;永久保留,合併是人工且罕見的操作,體積可忽略;鏈 A→B、B→C 在寫入 B→C 時順手把 A 改指 C,讀取仍沿鏈追、有迴圈防護)。
- **tombstone 讓多檔改寫可重入(review 第 4 則)**:合併是第一個「會刪東西」的多檔寫入,而 COMMIT 先傳 `tracks.json`、再逐檔傳 `pl__*.json`、沒有交易——中途失敗會讓 Drive 上有 items 指向已移除的 cid。有 tombstone 就能自癒:FETCH 載入後把每個清單的 item cid 經 `merged` 重導,改到的清單位元組與 Drive 不同,下一次 COMMIT 自然重傳;`Hydrate` 前也做同一步,所以 R-4 不會把懸空狀態忠實重建出來。T2b / T4 要有「COMMIT 在第 N 個 upload 失敗」的注入測試,斷言再跑一次 pull 之後 Drive 上不存在「item 的 cid 不在 `tracks` 也不在 `merged`」的狀態。
- 兩個 cid 對同一個 provider 持有**不同** id 是「不是同一錄音」的證據:不自動合併;人工仍堅持合併時,敗者那個 provider 的 id 進勝者的 `conflicts[]`,不靜默丟棄。
- **cid 一旦建立,除合併外永不改寫**:`p:` 開頭的 cid 之後對到帶 ISRC 的 mapping 也維持 `p:`(前綴只是歷史,不是語意)。

### 決策 22:`capy resolve` 的契約(附錄 A)

- `capy resolve [<清單>] [--provider P] [--dry-run] [--yes]`:預設掃**全部**已連結的清單(resolve 只增不刪,不像 pull 需要 `--all`);對每個 (清單, provider) 找出 items 裡缺該 provider mapping 的 cid → Layer 1 → Layer 2;≥85 自動寫入,走 `withCanonical`(Drive 先 SQLite 後、閘與 lock 同 pull);其餘印成 review 佇列的 TSV。
- **exit code**:`0` 無事可寫或已寫入(**review 佇列有東西仍是 0**——它是 TSV 列,不是失敗;cron 的 `resolve --yes` 不能因為永遠有幾首解不開而永遠報錯)、`1` 錯誤、`2` 有待寫入的自動 mapping 但沒有確認(`--dry-run`、非 TTY 沒給 `--yes`、終端機取消)。
- `capy resolve --review`:TTY 逐筆裁決(accept / skip / manual search / not available);非 TTY → 印佇列 TSV、exit 2(明確要求人工裁決卻沒有終端機)。
- `capy resolve pin <cid> <provider>:<id|none>`:腳本用的釘選;`none` = 不可得。釘選對到已屬另一 cid 的 id → 依決策 21 合併(TTY 要確認;非 TTY 要 `--yes`)。
- review 佇列的來源:(a) 找不到候選或最佳分數 <85;(b) 最佳候選已屬另一 cid;(c) `conflicts[]` 非空且該 provider 的 mapping 不是 pinned(髒 ISRC:同 ISRC 不同 metadata,spec §6.2 說「只印 stderr 太弱」的那條)。keep = 把現有 mapping 釘住(人確認過),之後不再出現。
- `pl pull` 結尾多一行提示「N 首尚未對應到 <provider>,跑 capy resolve」;pull 本身不做 resolve(API 成本與關注點分離)。

### 決策 23:Layer 1 / Layer 2 的具體規則(spec §5.1)

- **Layer 1**:目標 provider 以正規化 ISRC 反查;候選只留 ISRC 相同者;多筆時消歧序 = 專輯名(正規化)相同 > 時長差最小 > provider id 字典序最小(決定性;`Track` 沒有發行日,spec 原文的「較早發行」先拿掉)。信心 95。
- **Layer 2**:查詢字串 = `norm(title) + " " + norm(primary_artist)`,取前 10 筆;分數 = 60·JW(title) + 25·JW(primary artist) + 15·時長項(≤3 s 得滿分、≥30 s 得 0、中間線性);`live / remix / acoustic / cover / demo / instrumental / karaoke` 任一關鍵字只出現在一邊 → 分數上限 84(強制進 review);<60 不列為候選。**時長差 >3 s 的候選上限 84**(review 第 2 則:時長項歸零時 60 + 25 = 85 剛好越過門檻,等於「標題與藝人字串相同就自動寫入、時長不看」;時長是標題沒帶關鍵字時唯一能分辨 extended mix / radio edit / 隱藏軌的訊號,不能被 title + artist 的滿分蓋過去;時長項只用來排序候選)。分數以 **`floor`** 取整(偏保守:84.9 進 review),T3 的表格測試照這個規格驗,不照實作反推。`norm()`:小寫 → 全形 ASCII(U+FF01–FF5E)轉半形 → 去 `(feat. …)` / `[Remastered …]` / ` - Live` / ` - Remastered 2011` 這類後綴 → 去標點 → 空白壓縮;中日韓不斷詞。**不引入 `golang.org/x/text`**(NFKC 延後;全形轉半形手刻一個迴圈就夠)。Jaro-Winkler 以 rune 計算,自己寫(約 40 行)。
- **artist alias 表(五月天 / Mayday)延後**:ISRC 覆蓋 99%,跨語言藝名只影響 fuzzy 的 1%,先讓它進 review 用 manual search 解決。

### 決策 24:negative cache 延後,並寫下加回的觸發條件

spec §5.4 的三層快取中,`tracks.json` 的 mapping 就是跨裝置的正向快取,SQLite 鏡像就是本機正向快取,兩者 P3 已有。**negative cache 延後**:每次 `resolve` 對尚未解開的 cid 重查(Layer 1 一次 + Layer 2 一次),以真帳號 ~2,500 首、ISRC 覆蓋 99% 估算,穩態每次重查數十次 API,可接受。cron 的 `resolve --yes` **是支援的用法**(決策 22 的 exit code 就是為它設計的,review 第 6 則),所以觸發條件只留可量測的那一個:單次 `resolve` 的 API 呼叫超過 200 次(T4 超過時在 stderr 印一行提醒——觸發條件要有人看得到才會被觸發);屆時加 `resolution_cache` 純快取表(不進 `Dump`,不違反「刪 db 可重建」——重建只是慢一點)。

### T1 — SPI:ISRC 反查與單曲查詢
