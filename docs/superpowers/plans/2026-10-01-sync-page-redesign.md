## 0. 需求與現況

### 0.1 使用者的需求(2026-10-01,照錄)

1. 要有明確的文案引導使用者「同步是什麼」:會要先落地在本機(原話「先落地在 local」;這句跟實際寫入順序的出入見 §0.3 與 Q5)、在 Google Drive 上生成對應的清單作為正本;正本可從任一平台的清單帶過來;命名上允許不一樣。
2. 一開始可以從任一平台的任一清單點選,動態顯示平台清單,接著引導如何做到同步。
3. 如果是同步在既有的清單,會如何去除重複。
4. 表格比照「我的清單」;資訊量參考「搬家」與「我的清單」。

### 0.2 現況為什麼讓人不知所措(讀碼得到的,不是猜的)

1. **清單只能手打名稱,頁面不列任何清單。** 文字框在 `sync.js:9`,CLI 只認正本的名稱或 pid(`pull.go:130-152`);打平台上的清單名會得到 `pull.err.not_found` / `not_linked`(`pull.go:828-833`),兩句都叫人去跑 `capy pl link`,這一頁做不到。
2. **四顆動作鈕平鋪**(從平台更新 / 推到平台 / 雙向同步 / 去除重複,`sync.js:26-31`),沒說何時該按哪顆;「推到平台」是 strict,這台沒 pull 過或平台上有沒帶回的改動就 exit 3(`push.go:451,460-462`)。
3. **平台下拉寫死四家,不看登入狀態**(`provider.go:33`、`sync.js:11`)。
4. **「只看變更」預設勾著,而且寫完不會勾回去**(`sync.js:12-14`);勾著時 sync 沒變更就不寫 base(`sync.go:78-83`),所以照預設操作,剛連上的清單永遠不會從這一頁寫進 base。
5. **名稱留空就送 `--all`**(`sync.js:19-23`);一個連結都沒有時 exit 0 沒表(`pull.go:808-813`),頁面卻說「兩邊已經一致」(`sync.js:45`)。
6. **確認與挑選器會把人丟到「進階 › 主控台」**:`con.run` 沒傳 `promptHost`(`sync.js:38-47`),`reveal()` 切到 `#/console`(`console.js:481-483`)。搬家、清單、wiki 三頁都有傳。
7. **收尾說明不完整**:寫入成功只剩一張表;非 0 直接貼原文、沒剝 `Error: `(`sync.js:44`);按 ✕ 關掉確認會露出英文的 `Error: user aborted`(`web_prompt.go:323-331`、`web_run.go:284-287`)。
8. **stderr 的提示只進主控台**:尚未對應、這次沒檢查的平台、要手動刪的殘留、清單消失等(`resolve.go:502-517`、`dedup.go:86-88,117-119`、`pull.go:866,881,919`)。
9. **錯誤訊息叫人做的事這一頁都做不到**:超過閾值說「加 --force」(web 不准)、push 被拒說「先 capy pl pull」、skip 列叫人跑 `capy resolve`(找對應在清單頁)。
10. **變更表是英文機器欄位原文**(`table.js:20`、`sync.go:17`、`pull.go:724`),REMOVE 列只靠顏色;zh 的說明欄還寫「canonical 已移除 / 換序 / 改名」(`zh-TW.json:814-817`)。
11. **頁面不接前後文**:搬家的「讓兩邊之後保持同步 →」不帶清單過來(`move.js:444-446`;`app.js:135-149` 的 route 只把參數給 ISRC 頁);回到頁面不重讀。
12. **搬家完成給的下一步(`pl link … 再 pl sync`,`zh-TW.json:609`),同步頁做不到。**

### 0.3 會改變設計的事實

- **「先落地在本機」跟寫入順序相反。** 每個寫入命令都是鎖 → FETCH → 閘 → 改狀態 → COMMIT,COMMIT 時 **Drive 先寫、SQLite 後寫**(`pull.go:31-32`);SQLite 是快取,刪了能從 Drive 完整重建(CLAUDE.md 硬約束)。頁面讀的 `capy export` 只讀本機 state.db(`escape.go:34-35`),可能過時。文案照事實寫(§3.1),並列成 Q5。
- **名稱只在連結的那一刻能不同。** `pl link <名稱> <平台>:<id>` 找不到正本時用第一個參數當名字建(`pull.go:584-591`);但第一次 push(或 sync 的 push 半邊)只要 `wantName ≠ liveName` 就排一筆 rename(`push.go:230-234`、`canon/project.go:113-115`),Spotify / Apple / YouTube 都宣告 `CapPlaylistRename`,本機曲庫沒有(`local.go:75`)。變更表有 rename 那一列(`push.go:296`)。之後平台上改名,下一次 pull 會帶回正本(`derive.go:229-232`)。結論:除了本機曲庫,同步之後兩邊名字一樣,沒有旗標能長期不同(Q6)。
- **寫入前的確認範圍**:pull / push / sync / dedup 寫入前一定列表、由命令問確認(`confirmWrite`,`pull.go:705`);**`pl link` 不問**:找不到正本就直接建(`pull.go:584-591`),帶 `--create` 就直接在平台建清單(`pull.go:621`)。所以「納入」與「在 X 建一份」的第一步按下去就做(指南 `docs/guide.html:397` 已照實寫)。
- **平台清單不能直接當同步的目標**:pull / push / sync / dedup 只收正本的名稱或 pid(`pull.go:800-835`),從平台清單出發一定要先 `pl link`。
- **「同步到一份已經有歌的既有清單」,現有 CLI 沒有不重排的安全路線。** 這是需求 3 的核心,也是 Q1:
  - **用 pid 直接連**:`--new-only` 以 pid 指定時不擋(`pull.go:571-576`),連上之後第一次 pull 沒有 base,會照平台順序搬動正本、把平台上的重複帶進來(`derive.go:118,127-129,155-185,95-108`)。上一份計畫 §7 已列為不做。
  - **用搬家加進既有清單**:`migrateCanonical` 看的是**目標**(`migrate.go:437-482`):目標沒連時用**目標的名字**找或建正本。所以「先把來源交給 capy 建正本 X,再搬到既有的 Y」會得到兩份互不相干的正本。目標跟某份正本同名時,會沿用那份正本,接著在沒有 base 的情況下照目標順序重排它(`migrate.go:221-227,452-475`;讀碼推得、沒跑過,Q2 先用測試釘住)。
- **capy 怎麼認「同一首」**:cid 依序看 mapping、ISRC alias、公式(`identity.go:61-74`、`cid.go:15-20`),**不看歌名、歌手、時長**;歌名、歌手、時長只在 resolve 到另一個平台找對應時用(Layer 2 模糊比對,分數 ≥ 85 才自動寫入,`resolve.go:28`)。YouTube 沒有 ISRC,同一首的音訊版與 MV 是兩個 id(`ARCHITECTURE.md:96`)。
- **sync 本身不去重**:同一首出現多次是合法的(決策 13);push 以 cid 做 LCS 配對、照份數對齊(`canon/project.go:44-91`)。去重是 `pl dedup` 的事:正本形式會寫(pull 半邊 → 正本去重 → push 半邊,一張表一次確認,同平台 id 或同 ISRC 算同一首,留第一份,`dedup.go:17-30`、`canon/dedup.go:6-25`);`<平台>:<清單>` 形式只報告、不碰 Drive(`dedup.go:49-61`),帶任何旗標會回錯(`dedup.go:57-58`)。
- **base 是跨裝置的**:`mergedBase` 走 `MergeBase` 合併 Drive 上每一台的裝置檔(`push.go:74-79`、`canon/base.go:8`)。所以別台電腦或帶 `--yes` 的排程跑 `pl sync`,用的是同一份 base:任何「留到之後的 sync 再做」的改動,都可能在沒人看表時被做掉。
- **`pl sync --all` / `pl pull --all` 只要一個連著的平台在這台沒登入就整輪 exit 1**:`observeAndDerive` 每個連結先 `pf.provider(prov)`,失敗就回錯(`pull.go:860-862`),而且在 `foreignLink`(`pull.go:865`)之前。`resolve` 不同:建不起來的平台只跳過(`resolve.go:188-192`)。
- **`pl show <清單 ID> --provider <平台>` 可以直接讀平台清單**(`pl.go:100-141`;解析 id 在 `resolvePlaylistID`,`pl.go:67-98`;讀曲目在 `pl.go:128`),欄位 `ID / TITLE / ARTISTS / ALBUM / DURATION`(非 TTY 時長是毫秒,`search.go:53-65`)。**Apple 的 `pl list` 拿不到曲數**,TRACKS 一律是 `-`(`apple/client.go:358`、`pl.go:42-44`)。
- **路由**:`app.js:133` 的正則是 `^#\/([a-z]+)(?:\/([^/?#]+))?$`,帶參數要寫成 `#/sync/apple`;`#/sync?provider=apple` 不符、會落到搬家頁。
- **流程元件已經在「我的清單」寫好了,但全是 `initPlaylists` 的閉包**(`playlists.js:22-743`):讀各平台清單、標狀態、納入、在 X 建一份、同步這份、找對應、收尾規則 `outcome()`。兩頁各寫一份是最大的風險,所以 T1 先抽共用模組(§3.6)。

## 1. 設計讀法

**讀成:既有產品 UI 的改版(保留現有風格),對象是想讓幾個平台的清單保持一致的一般使用者;沿用 capy 網頁的深色、GeekGreen 單一主色、自家 vanilla CSS,不引入新框架。** design-taste-frontend 這份技能明說它不涵蓋多步驟的產品 UI,這次只借它的文案紀律(不用 em-dash、不寫空泛的字)、資訊密度與一致性鎖(一個主色、一套圓角、按鈕不換行),版面規則以「我的清單」「搬家」既有的為準。三個旋鈕:變化度 4、動態 3(只有既有的狀態轉換,不加裝飾動畫)、密度 5。

**分工(一句話)**:「我的清單」從正本看(看歌、點播、管連結與對應);「搬家」是一次性把歌複製到另一個平台、之後各走各的;**「同步」從平台上的一份清單出發,讓它開始持續同步(納入、在別處建一份、接到既有的清單),再加上回頭的人一鍵同步。**

## 2. 版面

由上到下五段,全部在 `#page-sync` 裡(`promptHost` 都在本頁,`reveal()` 不會切到主控台):

1. **頁首**:標題、lead、常駐的三則事實(含一張小示意圖)、`還想知道` 的 details。
2. **在同步的清單**:一張小表(清單 / 首數 / 連到 / 同步),右上 `全部同步`,下面是頁首流程區。來源是 export,零網路。
3. **讓一份清單開始同步**:兩欄。左 16rem = 平台卡(帶登入狀態)+ 那個平台的清單(按了才讀,`pl list`);右 = 選中那份:標題列、依狀態換的引導卡(只有一顆主要鈕)、右欄流程區、歌曲預覽表(`pl show`)。
4. 右欄流程區(就地寫入:步驟條、狀態句、變更表、capy 的確認提示)。
5. **進階**(收起的 details):現在的四顆鈕與「只看變更」,原封保留並修掉現況的硬傷。

| 條件 | 版型 |

## 3. 設計

### 3.1 「同步是什麼」的文案(需求 1)

三層,越往下越具體:lead(一句完整的模型,照實說確認範圍)→ 常駐的三則事實與小示意圖 → 「還想知道」(重複的歌、順序、一次最多拿掉幾首、這一頁的依據是這台的副本、搬家和同步不一樣)。關鍵句(zh;en 同義,en.json 是來源):

- lead:讓同一份清單在幾個平台上保持一樣:改了任何一邊,按「同步」,其他地方跟著改。加歌、拿掉、換位置、改名之前,capy 一定先列出要改什麼,你確認了才寫;建一份新的正本或平台清單並連上,按下去就會做。

### 3.4 CLI `pl link --merge`(Q1 選 B 時,T3,等決策 62)

`capy pl link --merge <name|pid> <provider>:<id|名稱> [--dry-run] [--yes] [--force]`

- **正本必須已經存在**,不會順手建;不能跟 `--create`、`--new-only` 一起用。`--force` 只越過刪除閾值,跟單一清單的 `pl pull <name> --force` 同規矩;頁面一律不送。

- **一個命令做完,同一把鎖、一張表、一次確認**(照 `dedup.go:22-25` 正本路徑的形狀):
  1. **先找對應**(Q1 子題 b 推薦 A):
     - 先拿正本的歌跟**那份清單自己的曲目**比:同 ISRC 用 `resolve.PickISRC`,其餘用 `resolve.RankFuzzy`(`internal/resolve/resolve.go:217,242`),候選只限那份清單,分數 ≥ 85 算同一首,而且**一對一**:同一個清單曲目只給分數最高的那首正本歌(同分取正本裡先出現的),其他正本歌落到下一步搜平台目錄。這一步不打搜尋 API,而且避開 YouTube 同一首有音訊版與 MV 兩個 id、目錄搜尋命中另一支的問題。**自動認成同一首的配對也列在表上**:`dir=resolve`、`action=map`,REASON「認成同一首(分數 {score})」,REASON_CODE 沿用 resolve 的 `isrc` / `fuzzy`(README ×2 代碼表補 `pl link --merge` 的 `dir=resolve` 列);這樣「一次確認」時看得到哪些被認成同一首,確認後這些 mapping 才寫進 Drive。
     - 比不上的,再照 `migrate.go:266-276` 的佔位 link 手法對這個平台跑 `planResolve`(搜整個平台目錄),讓正本有、那份清單沒有的歌拿到這個平台的 id,第 3 步才推得過去。代價:`--dry-run` 也會打這個平台的搜尋 API。
