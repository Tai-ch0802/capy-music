## 0. 需求與現況

### 0.1 使用者的需求(2026-10-01)

1. 要有明確的文案引導使用者「同步是什麼」:正本落地、在 Google Drive 生成對應的清單當正本;正本可從任一平台的清單帶過來;名稱可以不一樣。
2. 一開始可以從任一平台的任一清單點選,動態顯示平台清單,接著引導如何做到同步。
3. 同步到既有的清單時,會如何去除重複。
4. 表格比照「我的清單」;資訊量參考「搬家」與「我的清單」。

### 0.2 現況為什麼讓人不知所措(讀碼得到的,不是猜的)

1. **清單只能手打名稱,頁面不列任何清單。** 文字框在 `sync.js:9`,CLI 只認正本的名稱或 pid(`pull.go:130-152`);打平台上的清單名會得到 `pull.err.not_found` / `not_linked`(`pull.go:828-833`),兩句都叫人去跑 `capy pl link`,這一頁做不到。
2. **四顆動作鈕平鋪**(從平台更新 / 推到平台 / 雙向同步 / 去除重複,`sync.js:26-31`),沒說何時該按哪顆;「推到平台」是 strict,這台沒 pull 過或平台上有沒帶回的改動就 exit 3(`push.go:451,460-462`)。
3. **平台下拉寫死四家,不看登入狀態**(`provider.go:33`、`sync.js:11`)。
4. **「只看變更」預設勾著,而且寫完不會勾回去**(`sync.js:12-14`);勾著時 sync 沒變更就不寫 base(`sync.go:78-83`),所以照預設操作,剛連上的清單永遠不會從這一頁寫進 base。
5. **名稱留空就送 `--all`**(`sync.js:19-23`);一個連結都沒有時 exit 0 沒表(`pull.go:808-813`),頁面卻說「兩邊已經一致」(`sync.js:45`)。
6. **確認與挑選器會把人丟到「進階 › 主控台」**:`con.run` 沒傳 `promptHost`(`sync.js:38-47`),`reveal()` 切到 `#/console`(`console.js:481-483`)。搬家、清單、wiki 三頁都有傳。
7. **收尾說明不完整**:寫入成功只剩一張表;非 0 直接貼原文、沒剝 `Error: `(`sync.js:44`);按 ✕ 關掉確認會露出英文的 `Error: user aborted`(`web_prompt.go:323-331`、`web_run.go:284-287`)。
8. **stderr 的提示只進主控台**:尚未對應、這次沒檢查的平台、要手動刪的殘留、清單消失等(`resolve.go:502-517`、`dedup.go:86-88,117-119`、`pull.go:866,881,919`)。
9. **錯誤訊息叫人做的事這一頁都做不到**:超過閾值說「加 --force」(web 不准)、push 被拒說「先 capy pl pull」、skip 列叫人跑 `capy resolve`(找對應在清單頁)。
10. **變更表是英文機器欄位原文**(`table.js:20`、`sync.go:17`、`pull.go:724`),REMOVE 列只靠顏色。
11. **頁面不接前後文**:搬家的「讓兩邊之後保持同步 →」不帶清單過來(`move.js:444-446`;`app.js:135-149` 的 route 只把參數給 ISRC 頁);回到頁面不重讀。
12. **搬家完成給的下一步(`pl link … 再 pl sync`,`zh-TW.json:609`),同步頁做不到。**

### 0.3 會改變設計的事實

- **「先落地在本機」跟寫入順序相反。** 每個寫入命令都是鎖 → FETCH → 閘 → 改狀態 → COMMIT,COMMIT 時 **Drive 先寫、SQLite 後寫**(`pull.go:31-32`);SQLite 是快取,刪了能從 Drive 完整重建(CLAUDE.md 硬約束)。頁面讀的 `capy export` 只讀本機 state.db(`escape.go:34-35`),可能過時。文案照事實寫(§3.1),並列成 Q5 請使用者確認。
- **名稱只在連結的那一刻能不同。** `pl link <名稱> <平台>:<id>` 找不到正本時用第一個參數當名字建(`pull.go:584-591`),所以連結時可以不同;但第一次 push(或 sync 的 push 半邊)只要 `wantName ≠ liveName` 就排一筆 rename(`push.go:230-234`、`canon/project.go:113-115`),Spotify / Apple / YouTube 都宣告 `CapPlaylistRename`,本機曲庫沒有(`local.go:75`)。變更表有 rename 那一列(`push.go:296`),使用者看得到、確認才改。之後平台上改名,下一次 pull 會帶回正本(`derive.go:229-232`)。結論:除了本機曲庫,同步之後兩邊名字一樣,沒有旗標能長期不同(Q6)。
- **平台清單不能直接當同步的目標**:pull / push / sync / dedup 只收正本的名稱或 pid(`pull.go:800-835`),從平台清單出發一定要先 `pl link`。
- **「同步到一份已經有歌的既有清單」,現有 CLI 沒有不重排的安全路線。** 這是需求 3 的核心,也是 Q1:
  - **用 pid 直接連**:`--new-only` 以 pid 指定時不擋(`pull.go:571-576`),連上之後第一次 pull 沒有 base,會照平台順序搬動正本、把平台上的重複帶進來(`derive.go:118,127-129,155-185,95-108`)。上一份計畫 §7 已列為不做。
  - **用搬家加進既有清單**:`migrateCanonical` 看的是**目標**(`migrate.go:443-482`):目標沒連時用**目標的名字**找或建正本。所以「先把來源交給 capy 建正本 X,再搬到既有的 Y」會得到兩份互不相干的正本。更糟的是目標跟某份正本同名時,會沿用那份正本,接著在沒有 base 的情況下照目標順序重排它(`migrate.go:221-227,460-475`;讀碼推得、沒跑過,Q2 先用測試釘住)。
- **sync 本身不去重**:同一首出現多次是合法的(決策 13);push 以 cid 做 LCS 配對、照份數對齊(`canon/project.go:44-91`)。去重是 `pl dedup` 的事:正本形式會寫(pull 半邊 → 正本去重 → push 半邊,一張表一次確認,同平台 id 或同 ISRC 算同一首,留第一份,`dedup.go:17-30`、`canon/dedup.go:6-25`);`<平台>:<清單>` 形式只報告、不碰 Drive(`dedup.go:49-61`),帶任何旗標會回錯(`dedup.go:57-58`)。YouTube 沒有 ISRC,同一首的音訊版與 MV 是兩個 id,抓不到(`ARCHITECTURE.md:96`)。
- **base 是跨裝置的**:`mergedBase` 走 `MergeBase` 合併 Drive 上每一台的裝置檔(`push.go:79`、`canon/base.go:8`)。所以新的「合併連結」只要在 Drive 寫 `SetBase`,別台就不會碰到「沒有 base 的第一次 pull」。
- **`pl sync --all` / `pl pull --all` 只要一個連著的平台在這台沒登入就整輪 exit 1**:`observeAndDerive` 每個連結先 `pf.provider(prov)`,失敗就回錯(`pull.go:854-858`),而且在 `foreignLink` 之前。`resolve` 不同:建不起來的平台只跳過(`resolve.go:188-192`)。
- **`pl show <清單 ID> --provider <平台>` 可以直接讀平台清單**(`pl.go:58-88`),欄位 `ID / TITLE / ARTISTS / ALBUM / DURATION`(非 TTY 時長是毫秒,`search.go:53-65`);比對是 `r.ID == arg || HasSuffix(r.ID, "/"+arg)`(`pl.go:75-77`),頁面一律傳完整 id。
- **路由**:`app.js:133` 的正則是 `^#\/([a-z]+)(?:\/([^/?#]+))?$`,帶參數要寫成 `#/sync/apple`;`#/sync?provider=apple` 不符、會落到搬家頁。
- **流程元件已經在「我的清單」寫好了,但全是 `initPlaylists` 的閉包**(`playlists.js:22-743`):讀各平台清單、標狀態、納入、在 X 建一份、同步這份、找對應、收尾規則 `outcome()`。兩頁各寫一份是最大的風險,所以 T1 先抽共用模組(§3.6)。

## 1. 設計讀法

**讀成:既有產品 UI 的改版(保留現有風格),對象是想讓幾個平台的清單保持一致的一般使用者;沿用 capy 網頁的深色、GeekGreen 單一主色、自家 vanilla CSS,不引入新框架。** design-taste-frontend 這份技能明說它不涵蓋多步驟的產品 UI,這次只借它的文案紀律(不用 em-dash、不寫空泛的字)、資訊密度與一致性鎖(一個主色、一套圓角、按鈕不換行),版面規則以「我的清單」「搬家」既有的為準。三個旋鈕:變化度 4、動態 3(只有既有的狀態轉換,不加裝飾動畫)、密度 5。

**分工(一句話)**:「我的清單」從正本看(看歌、點播、管連結與對應);「搬家」是一次性把歌複製到另一個平台、之後各走各的;**「同步」從平台上的一份清單出發,讓它開始持續同步(納入、在別處建一份、接到既有的清單),再加上回頭的人一鍵同步。**

## 2. 版面

由上到下五段,全部在 `#page-sync` 裡(`promptHost` 都在本頁,`reveal()` 不會切到主控台):

1. **頁首**:標題、lead、常駐的三則事實(含一張小示意圖)、`還想知道` 的 details。
2. **在同步的清單**:一張小表(清單 / 首數 / 連到 / 同步),右上 `全部同步`,下面是頁首流程區。來源是 export,零網路。
3. **讓一份清單開始同步**:兩欄。左 16rem = 平台卡(帶登入狀態)+ 那個平台的清單(按了才讀,`pl list`);右 = 選中那份:標題列、依狀態換的引導卡(只有一顆主要鈕)、右欄流程區、歌曲預覽表(`pl show`)。
4. 右欄流程區(就地寫入:步驟條、狀態句、變更表、capy 的確認提示)。
5. **進階**(收起的 details):現在的四顆鈕與「只看變更」,原封保留並修掉現況的硬傷。

| 條件 | 版型 |
|---|---|
| `#page-sync` 容器 ≥ 64rem | 兩欄,左 16rem(沿用 `.pl__cols`,`app.css:253-254`) |
| < 64rem | 疊成一欄:左欄在上,清單列限高 15rem 自己捲 |
| 歌曲預覽表容器 ≥ 50rem | 一首一行:# 3rem、歌曲、時長 4.5rem、(Spotify 時)12rem 的「在 Spotify 上聽」 |
| 歌曲預覽表容器 < 50rem | 一首拆多行(沿用 `.pl__songs` 的規則,`app.css:335-347`) |
| 變更表 / 在同步的清單容器 < 40rem | 每列拆兩行 |

所有表都在 `.tbl-wrap--tall` 裡(60vh、表頭黏住、裡面捲);頁面不跟著曲數變長,任何寬度都不橫向捲動。

### 2.4 選中一份有同名正本的清單

- **同名、那份正本在這個平台沒有連結**:引導卡說「capy 已經保管一份同名的正本「太好聽」(612 首),它還沒連到 Spotify。」主要鈕「連到正本「太好聽」」打開 §2.5 的確認卡(Q1 選 B 時);不選 B 時沒有主要鈕,照實說「這一版還不能把兩份都有歌的清單接起來同步;在 Spotify 上改名後再納入,會變成另一份獨立的正本,不會跟「太好聽」同步。」
- **同名、那份正本已經連著這個平台的另一份**:只有說明,沒有主要鈕(一份正本在每個平台只連一份)。

### 3.1 「同步是什麼」的文案(需求 1)

三層,越往下越具體:lead(一句完整的模型)→ 常駐的三則事實與小示意圖 → 「還想知道」(重複的歌、順序、一次最多拿掉幾首、這一頁的依據是這台的副本、搬家和同步不一樣)。關鍵句(zh;en 同義,en.json 是來源):

- 正本在你的 Google Drive:capy 先寫進 Drive,再更新這台電腦上的副本;副本只是快取,刪掉也能從 Drive 完整拿回來,換一台電腦也接得回來。
- 從哪一份開始都可以:Spotify、Apple Music、YouTube Music 或本機曲庫上的任何一份清單,都能納入 capy 當正本。
- 名字只在連的那一刻能不同:第一次同步會把平台上的清單改成正本的名字(變更表裡有一列改名,你確認了才改);之後在任何一個平台改名,會帶到正本和其他平台。本機曲庫的檔名不改。
- 同步不會替你去掉重複:同一首在清單裡出現兩次是允許的,各平台照份數對齊。capy 認同一首的依據依序是:對應過的平台 id、ISRC,最後才看歌名、歌手和時長。YouTube Music 沒有 ISRC,同一首的音訊版和 MV 會算成兩首。

標點:zh-TW.json 全目錄只有 。、「」 用全形,其餘 `, ; : ( ) ?` 半形;任何新字串都不用破折號(`dedup_note` 原文的破折號這次一起拿掉)。

### 3.2 從任一平台的任一清單開始(需求 2)

### 3.4 CLI `pl link --merge`(Q1 選 B 時,T3,等決策 62)

`capy pl link --merge <name|pid> <provider>:<id|名稱> [--dry-run] [--yes]`

- **正本必須已經存在**,不會順手建;不能跟 `--create`、`--new-only` 一起用。
- **前置檢查**(任何一條不過都 exit 1、零寫入):沿用一般 link 的 `link.err.not_listed` / `unreadable` / `taken`;那份正本在這個平台已有連結時不接管(不管是不是別台、別帳號的);那份清單寫不進去時擋下(`PlaylistRef.Unwritable`,`provider.go:135-137`:Apple 的 canEdit:false 與協作清單、YouTube 別人的與自動清單已會標;Spotify 非擁有者非協作的要補判斷,Q7)。
- **只寫 Drive,三件事**:① 把那份清單裡正本還沒有的歌,照它的順序接到正本尾端,同一首只接第一份(依序看 mapping、ISRC alias、公式,同 `migrate.go:238-256` 的迴圈,抽成函式兩邊共用);② 寫 `Links[p] = id`;③ `SetBase(pid, p, 那份清單的真實快照)`。
- **之後**:下一次 pull 的 base 等於平台現況,沒有任何變更(別台經 `MergeBase` 拿到同一份 base);重排、拿掉那份清單裡重複的份、改名、補上正本有的歌,全部交給後面的 `pl sync`,用它現成的變更表、移除閾值(`pull.go:718-722`)與確認。
- **表與確認**:表沿用 `pullHeader`,ACTION 只會是 add 或 skip(skip = 那份清單裡多出來的同一首,REASON_CODE 沿用 `dup_id` / `dup_isrc`,不新增代碼);確認用 `confirmWrite`;`--dry-run` 或非 TTY 沒帶 `--yes`:印表後 exit 2、零寫入;沒有東西可接:不問確認,照一般 `pl link` 寫連結與 base,stderr 說「正本已經有這份清單的每一首」。既有 `pl link` 的輸出一個字都不變。
- **決策 38 的例外**:那份既有平台清單會在 `pl sync` 被排成正本的順序,撞 CLAUDE.md「任何路徑都不得排序或打亂清單」。決策 62 把例外限縮成「使用者明確選了合併、每一筆 move 都在變更表、確認才寫」,CLAUDE.md 那一條同 PR 補這個例外。留哪一份重複由 push 的 LCS 決定,不一定是先出現的那份(結果清單一樣,差別只在平台上那一列的加入時間),照實寫、不承諾。
- **同 PR 要改的兩句**:搬家頁「capy 沒有任何路徑會打亂它」(zh-TW.json:1284 與 en);`migrate.summary.source_unlinked`(zh-TW.json:609)現在叫人跑不帶 `--new-only` 的 `pl link` 再 `pl sync`,正是會重排正本的那條路,改成指向 `--merge`。
