## §1 已拍板的決策(附錄 C 決策 33–37)

### 決策 33:`local` 是第一個**綁裝置**的 provider;link id 帶 device id,SPI 加 `CapDeviceBound` + `DeviceScoped`

**問題。** `pl__<pid>.json` 的 `links` 是共享檔(所有裝置都讀寫),但本機曲庫只在一台機器上。裝置 A `pl link 通勤 local:通勤.m3u8`;裝置 B 跑 cron 的 `pl sync --all`:B 的 `ListPlaylists` 沒有那個檔 → `observeAndDerive` 判成 gone → Q6 自動 unlink → `pl__` 上傳 → **A 的連結被 B 刪掉**。`push --all` 在 B 上則是 refused「找不到清單」把 B 整輪擋住。這是 SPI 的第一個偷渡假設:**provider id 與 link 被當成全域有意義**。

**定案。**
- local 的 playlist id = `<device_id>/<檔名>`(device_id 就是 `config.DeviceID`,ULID;provider 建構時拿到;空的(還沒 `auth login google`)就拒建、指路登入)。**track id 不帶 device 前綴**——只是正規化相對路徑,cid `p:local:<路徑>`(2026-09-08 PR #37 review 改:T0 原本讓 track id 也帶 device,理由是「兩台裝置同一相對路徑放不同歌不會撞」;但接管(Q30)正是為重灌設計的,而重灌就是 device_id 變了,帶 device 的 cid 會讓每一首沒 ISRC 的本機曲目在接管後的第一次 pull 分裂成兩首、下一次 push 再把重複的送去別的平台。foreign 的判斷看的是 `Links` 的 playlist id,track id 不需要 device;同路徑不同歌是接受的取捨,Q31)。
- SPI 加能力位元 `CapDeviceBound`(bit 15,尾端;`CapSearch` 是 bit 0、`CapPlaylistRename` 是 bit 14)與介面 `DeviceScoped { Foreign(id string) bool }`:id 屬於別台裝置就是 foreign。CLI 對 foreign 的 link:pull / push / sync 一律 stderr「跳過 通勤 的 local:屬於裝置 <id>」,**不算 gone、不算 refused、不動 base**;`pl link` 只能連本機的(輸入相對路徑或檔名,provider 自己補前綴);`pl unlink` 任何裝置都可以(那是 canonical 的事)。
- `manifest.devices` 已有 device 的 `name`(hostname),訊息用它,沒有就印 id。
- **一個 canonical 清單同時只連一台裝置的 M3U**(`Links` 一個 provider 一格,PR #34 review):兩台筆電各有一份 `通勤.m3u8` 都想跟 Spotify 對齊是做不到的,這是「local 綁裝置、不是網路共享」的代價,README 第一段就要講(§5)。
- **`pl link` 撞到別台裝置的 local link → 接管(re-home)**(Q30,建議接管):`Links["local"]` 改成本機的 id,stdout 說「原本連到裝置 <name>,已改為本機」;原裝置下一輪起變 foreign、只跳過。這同時是 **device_id 變了**(重灌、`CAPY_CONFIG_DIR` 換目錄 = 新裝置)之後的復原路徑:舊 link 變 foreign 靜靜停掉,使用者重跑一次 `pl link` 就接回來,訊息要指路(foreign 的 stderr 那行直接說「要在這台接手:capy pl link <清單> local:<檔名>」)。拒絕的設計則需要另一條 re-home 指令,否則重灌就是死路——所以不採。
- 不做的:不做「把別台的曲庫也讀進來」(那是網路共享,不是 local);不做 device 對 device 的檔案搬運。

### 決策 34:id = 正規化相對路徑;rename / move = remove + add;升級路徑是內容 hash

- 路徑相對於 `local_root`,一律 forward slash、去 `./`、Unicode NFC(macOS 檔案系統可能回 NFD,同一個中文檔名兩台機器要算同一個 id;Q26),大小寫保留。
- 曲目改名 / 搬家 = 下一次 pull 看到 remove + add(cid 變了);對「驗證 SPI」夠用,對真的曲庫管理不夠——升級路徑 = `capy local scan` 算內容 hash 當 id(rename-safe、跨裝置),**列出不建**。
- cid 含 `/`、空白、非 ASCII、可能含 `:`(Windows 的 `C:` 不會出現,因為是相對路徑;檔名含 `:` 在 macOS 合法):T1 先 grep canon / resolve / store / cli 確認沒有任何地方把 cid 或 provider id 以 `:` 切開,確認後在 spec §6.2 註明「cid 是不透明字串」;有的話那也是一條發現。

### 決策 35:讀端——`local_root` 下的 `*.m3u8` / `*.m3u` 是清單、`library.json` 是曲庫;`Search` 必做

- `capy config set local_root <目錄>`(config 欄位 `local_root`,非機密);沒設 → `newProvider("local")` 回可行動的錯誤(「先 capy config set local_root」),Health 同。
- 清單:root 這一層的 `*.m3u8` / `*.m3u`(不遞迴,Q25);`PlaylistRef{ID: <device>/<檔名>, Name: 去副檔名的檔名, Total: 行數}`;內容 = 非 `#` 開頭的每一行是一個相對路徑(相對於 M3U 檔所在目錄,再正規化成相對於 root);`#EXTINF` 只在曲庫沒有那首時當備援標題,不當 source of truth。
- 曲庫:`<root>/library.json`,schema `{"schema_version": 1, "tracks": {"<相對路徑>": {"title", "artists": [], "album", "duration_ms", "isrc"}}}`;由使用者(或未來的 `capy local scan`)維護,**P6 不讀音訊 tag、不加相依**(Q27)。清單裡有、曲庫沒有的路徑:仍是一首(id = 路徑,標題 = `#EXTINF` 或檔名),`Unpushable` = false(它就在本機),但 `Pushable` 只認曲庫裡的(決策 36)。
- 能力:`CapPlaylistRead`、`CapSearch`(曲庫內,標題 + 藝人正規化後子字串比對;正規化若要用 `internal/resolve` 的 `Norm`,T1 先看 import graph——provider 不該依賴 resolve,必要時把 `Norm` 下沉到 `provider` 或複製最小版本)、`CapISRCExpose` / `CapISRCLookup`(曲庫有 `isrc` 的那些;`LookupISRC` 直接查索引)、`TrackGetter`(路徑存在即回)、`CapDeviceBound`。**不做**:播放(`play` 對 local 一律 ErrNotSupported;Q28)、`auth login local`(沒有憑證)、`CapPlaylistCreate`。
- gone:本機檔不存在才是 gone(foreign 不是);Restricted / AuthExpired / rate limit 這三族錯誤 local 都沒有——`friendlyErr("local", …)` 要有自己的分支(路徑不存在、沒權限、`library.json` 壞掉),**每一個 n/a 都寫進 §2**。

### 決策 36:寫端——整檔改寫(temp + rename),`Pushable` = 路徑在曲庫;全部 ops 都支援

- `ApplyOps`:用 `provider.ApplyPlaylistOps(current, ops)` 算目標序列,整檔重寫(`#EXTM3U` 一行 + 每首一行相對路徑;**丟掉其他工具寫的 `#EXTINF` 與註解**,計畫講明、README 講明)→ 寫到同目錄的暫存檔 → `os.Rename` 原子取代;`rename` = 改檔名(同目錄,`.m3u8`);`skipped` 恆 nil。**平台端沒有 CAS 沿用 T4 的套用前重讀比對**,不做 mtime CAS(局部檔案的競態窗口是毫秒級,重讀已足夠;要做也只是 `os.Stat` 比 ModTime,列為升級路徑)。
- `Pushable(id)` = 去掉 device 前綴後的路徑在 `library.json` 裡且是本機的 id(foreign 一律 false);`PartialWriteError` 不會發生(一次寫入)。
- 能力:`CapPlaylistAppend | Remove | Reorder | Rename`——是第一個「全部 ops 都支援、沒有 append-only 例外」的寫端,正好跟 Apple(決策 30)成對照。

## §2 SPI 假設清單(P6 的真正產出;T1–T3 填完,2026-09-08 定稿)

**結論:SPI 撐得住 local。** 讀端 / 寫端 / 身分 / resolver / pull / push / sync 全部走原本的能力介面,沒有為 local 開任何特例分支(A13 是 CLI 沒照 spec 做,不是 SPI 的洞——第一個不宣告 Rename 的 writer 就把它照出來);唯一新增的 SPI 語意是決策 33 的 `CapDeviceBound` + `DeviceScoped`(A1),那是所有「非全域 id」的 provider 都需要的,不是 local 專屬。接 YouTube Music / Tidal 之前要先補的(保留意見):(1) A12——若那個平台的 rename 會改 id,`PlaylistWriter` 要能回新 id,目前只能 skip;(2) A10——foreign mapping 的 skip 理由要能區分「local file」與「別台裝置的 id」,現在共用一句;(3) A2——`friendlyErr` 是一個 switch,每加一個平台就多一組分支,第四個平台時值得改成 provider 自己回可行動訊息;(4) A6——`Search` 的正規化各平台各寫,local 用最小版,第三個要模糊比對的平台出現時把 `resolve.Norm` 下沉到 `provider`。
