## §1 本次拍板的決策(2026-09-08;附錄 C 決策 26–32)

### 決策 26:不建 op log / HLC;同步模型 = per-device base + 三方語意的 DERIVE + 共享檔版本守衛

v0.5 的 op log(§6.4)是在「所有裝置寫同一份狀態」的前提下設計的:沒有 per-device base,就只能靠 ops 的全序(HLC)replay 出一致結果。P3 把 base 搬進 `dev__<device_id>.json` 之後,前提變了:

1. **每台裝置對每個平台都有自己的「上次對齊狀態」**,DERIVE 對最新的 C 算 delta 再套上去。兩台裝置各從不同平台 pull,只要 COMMIT 序列化,delta 自然疊加(A 先 commit C+ΔS,B FETCH 到它再疊 ΔA)。這就是三方合併,不需要 replay。
2. **沒有本機編輯命令,op log 沒有東西可記。** 每一筆 canonical 變更都是「觀測到平台跟 base 不同」,而觀測是可重做的(下次 pull 再算一次)。離線佇列也因此不存在:pull / push 都要 Drive,離線就是失敗、下次再跑。
3. 真正的洞不是缺 op log,是**共享檔的 lost update**:FETCH 到 COMMIT 之間別台裝置寫了 `pl__`,我方 COMMIT 蓋掉、而我方 `dev__` 的 base 已前進 → 對方 derive 出來的變更永遠不會再被 derive(base 對得上平台、C 卻少了)。這用版本守衛擋(決策 29),不用 op log。

**代價(要讀清楚):**
- **沒有 base 的裝置會復活別台裝置刪掉的歌**:X 在 Spotify 被刪、裝置 A pull 後 C 沒有 X、但還沒 push 到 Apple;裝置 B(新裝置、第一次 pull 剛連結的 Apple,**或同一台老裝置 `pl unlink` 再 `pl link`**——base 只對目前連結的那個平台清單有效,relink 就清掉了,§6.3)pull Apple 時沒有 `base_Apple`,規則 4 的 bootstrap 語意把 L 全部當新增 → X 回到 C。窗口 = 「A 端刪除已 pull、尚未 push 到 B 平台、B 裝置對 B 平台無 base」三者同時成立;任何一台裝置跑一次 `pl sync` 就關掉窗口,而且復活會以 `add` 列出現在 B 裝置的 pull 輸出(`--dry-run` 看得到)。**Q15:接受並文件化(建議),或給 `pl__` 加 item 級 tombstone(`removed{cid: ts}`、30 天過期)。** 這是 v0.5「tombstone 必須保留」那句話在新模型裡唯一還沒被規則 4′ 涵蓋的情境。
- `rename` 與順序衝突沒有 HLC 可比:兩台裝置(或同一台的兩個平台)對同一清單分別 pull 到不同名字 / 不同順序 → 後 COMMIT 者勝。規則 7 是「平台名 ≠ base 名才改」、規則 6′(決策 27)是「平台順序 ≠ base 順序才採平台順序」,所以只有**兩邊真的都改了**才會互蓋,版本守衛保證後者看得到前者的結果再決定。
- 如果將來加 `pl add/remove/move`:它們直接改 C、走同一個 `withCanonical`(FETCH → 改 → 版本守衛 → COMMIT),仍然不需要 op log;離線編輯要佇列時才回頭看 §7 的重建策略。

### 決策 27:DERIVE 規則 4 與 6 改為 base-aware(三方語意),與規則 5 對稱

現況:規則 5(移除)只在 base 存在時發生、上限 b − l;規則 4(新增)**不看 base**,L 裡配不到 C 的出現一律 add。單平台時沒差;雙平台時:使用者在 Spotify 刪了 X → Spotify pull 從 C 移除 X → Apple pull 看到 L 有 X、C 沒有 → **把 X 加回來**。push 到 Apple 時就沒有東西可刪,刪除意圖丟失;`pl sync` 的結果甚至取決於先 pull 哪個平台。這正是 v0.5 寫 tombstone 要擋的情境。

新規則 4′:base 存在時,cid X 在 L 裡配不到 C 的出現,**只有超出 base 計數的部分才是新增**——l(X) − b(X) > 0 才 add,至多 add 這麼多個,取 L 順序最後的那幾個(平台新增通常在尾端;鏡像規則 5「依 rank 由後往前移除」);其餘配不到的出現是「平台還沒跟上 C 的移除」,留給 push 去刪。沒有 base 時全部 add(bootstrap,不變)。

**規則 6(換序)有同一個病,而且單一使用者兩個平台就會咬到**:C = S = A = [a, b, c],兩邊 base 相同;使用者把 Spotify 改成 [c, a, b];`pl sync`:pull S → C = [c, a, b];pull A → L_A = [a, b, c] 跟 base 一樣沒動,規則 6 卻把配對上的 item 排成 L 的順序 → C = [a, b, c];push S → Spotify 被改回 [a, b, c],重排被靜默取消。今天每次 pull 另一個平台就已經會把 C 的順序翻回去,只是沒有東西 push 回平台所以沒人發現。新規則 6′:base 存在時,**只有平台真的重排了才採 L 的順序**——「重排」= L 的 id 序列拿掉 base 沒有的、與 base 的序列拿掉 L 沒有的,兩者不同(重複曲目以出現序配對;精確定義 T3 定);沒重排 → 配對上的 item 保留 C 的 rank(新增 / 移除照規則 4′ / 5);兩邊都重排 → 後 pull 者勝(決策 26 已接受的那種衝突)。沒有 base → 維持今天的行為(採 L 順序)。

**這是改 DERIVE 語意的 PR,必須跟 push 一起出**(T3 + T4 相鄰):只有 pull 的世界裡,規則 4′ 會讓 C 跟平台脫節而沒有東西去對齊。T2b 說過「T2b 是唯一改 DERIVE 的 PR」,P5 T3 是第二個,理由寫在這裡。3000 組隨機性質測試要擴成多平台 / 多裝置的 pull-push 序列,**oracle 是意圖不是收斂**(§3 T3)。

### 決策 28:`pl push` 的契約(附錄 A)

`capy pl push [name|pid] [--provider P] [--all] [--dry-run] [--yes] [--force]`,形狀與 exit code 完全鏡像 `pl pull`(0 無變更 / 已套用、1 錯誤、2 待套用、3 安全閥)。對每個目標 (清單, provider):

1. **前提一:base 存在**(本裝置對這個平台清單 pull 過)。沒有 → exit 3、零寫入,訊息「先 `capy pl pull`」。不然 diff(L, project(C)) 會把平台上所有不在 C 的曲目刪光——這是「首次 pull 永不移除」的 push 版。
2. **前提二:平台沒有未 pull 的變更**:L 的快照(平台清單 id、名稱、依平台順序的 provider id)與 base 的快照**直接比對**(`snapshotEqual` 已存在),不同 → exit 3,訊息「平台有未 pull 的變更,先 `capy pl pull`(或用 `pl sync`)」。**不能用 Derive(base, L) 是否為空來判**:Derive 是 L 對 C 的差,push 前 C 通常剛被另一個平台改過(那正是要 push 的東西),Derive 會報一堆 move / add,把正常的 push 擋掉。push 蓋掉使用者剛在平台改的東西是不可接受的。`pl sync` 先 pull 後 push,兩個前提由建構保證。
3. **對齊鍵是 cid,不是 provider id**(同 §6.5.1 規則 1;PR #30 review 改):want = C 的 items 依 rank 的 cid 序列,live = L 經身分規則算出的 cid 序列(OBSERVE 已經算了)。以 LCS 配對(重複照算,與規則 2 同一套)。**配對上的 item 不動**——所以「pinned 成不可得、但曲目此刻就在平台上」與「Apple 沒有 catalog 對應的 library-only 曲目(`i.` id)」都會配上、不會被當成 remove(這正是 review 抓到的洞:若以 provider id 序列 diff 投影,被 skip 的 item 只要人還在平台上就會被排進 remove)。
4. **變更集**:配不到的 L 出現 → `remove`(provider id 取 L 原文,永遠有);配不到的 C item → 要 `tracks[cid].mappings[P].id` 才能 `add`,沒有(無 mapping、pinned 不可得、Apple 只有 library id)→ 列成 `skip`(reason 指向 `capy resolve`)並從 want 拿掉,不阻擋其他曲目——所以純 `skip` 只剩「C 有、平台沒有、又推不出去」;配對上但順序不同 → `move`;`rename`(C.name ≠ L.name 且 provider 支援改名)。TSV 欄位與 pull 一樣 `action pos cid provider_id title artists reason`,再加 `skip` / `manual`。不可推的項目(Spotify local file、library-only)在 L 裡幾乎一定也在 C(它們只能經這個平台進 C),配對後不動;Spotify 的整批取代加不回 local file,所以**含 local file 的 Spotify 清單在最小操作(Q19 B)完成前拒絕 push**(exit 3、訊息講明是哪幾首;Q22)。
5. **安全網**:`remove` 數過決策 18 的閾值(分母 = L 的長度),超過 → exit 3、`--force` 才越過且只能配單一清單;`--dry-run` 只印、exit 2(有變更)/ 0,不碰平台也不碰 Drive;非 TTY 沒 `--yes` → exit 2;TTY 確認。
6. **套用**:`provider.ApplyOps(ctx, id, current, ops)`(T1;`current` = 剛觀測到的 L);provider 對某類 op 回 `ErrCapability`(Apple 的 remove / move)→ 那些列標成 `manual`(「Apple 端請手動」),其餘照做。
7. **驗證與前進 base——ApplyOps 成功或失敗都做**:套用後(或 ApplyOps 回錯後)**重讀 L′**,L′ ≠ want(平台拒收某首、順序被平台正規化、或 Spotify 的 `PUT` + `POST` 分批做到一半斷網)→ stderr 警告;base[pid][P] := L′ 的快照(id 原文 + 觀測當時的 cid,與 pull 同一個 Observe 路徑)。base 的定義是「本裝置上次看到的平台狀態」,不是「上次成功同步的狀態」:分批做到一半死掉、base 不動的話,下一次 pull 看到 b = 250、l = 100 會算出 150 筆 remove、閾值擋下、使用者被問要不要 `--force`——真相卻是我們自己的殘局(PR #30 review)。base 推到 L′ 後 `pl__` 沒變,下一次 push 自然把沒送出去的那幾批補上。**`pl__<pid>.json` 不變**(items / rank / name 都不動);`tracks.json` 可能因 Observe 補 mapping / conflicts 而變。
8. **COMMIT**:走 `withCanonical` 同一套(版本守衛 → tracks → pl__ → dev__ → manifest → SQLite)。ApplyOps 失敗時**仍然 COMMIT**(base 要落地),COMMIT 完再以 exit 1 結束並講明平台改了幾批。全部套用成功、Drive 上傳失敗 → base 沒前進,下次 pull 會把我們剛 push 的東西當「平台變更」再 derive 一次:LCS 對同 cid 會配上、零變更,**不會重複**,訊息照 pull 的「本機快取未動,下次 pull 重算」。

**Spotify 的套用策略**:任何 add / remove / move → 整批取代:`PUT /playlists/{id}/items`(前 100 首)+ `POST /playlists/{id}/items?position=`(其後每 100 首一批);`rename` → `PUT /playlists/{id}`。取代會丟掉 Spotify 端每首的 `added_at` / `added_by`,而且加不回 local file(Q19、Q22;升級路徑是逐條 DELETE / POST / PUT range 的最小操作,並帶 `snapshot_id` 做樂觀鎖)。`ApplyOps` 拿 CLI 已觀測到的現況 `current` 當基準模擬 ops,不在 provider 裡再讀一次(少一次 API、少一個競態窗口)。只有使用者自己或協作的清單可寫,403 → 友善訊息。

### 決策 29:共享檔版本守衛(lost update 變成可偵測、可重跑)

COMMIT 前**再跑一次 FETCH 用的 `files.list`**(fields 已含 `version`),對 **FETCH 時讀過的每個檔**(`s.fetched` 全部,不只這次要上傳的)比對記下的 `File.Version`,以及同名檔的份數(別台裝置在我們 FETCH 之後 Create 的算變動);任一不同 → **一個檔都不傳**、本機不動、exit 1,訊息「Drive 上的 X 在這次執行期間被別台裝置改過;重跑一次」。為什麼是讀過的每個檔而不是 staged 的:這次沒變的檔也參與了決策——item cid 在 FETCH 時經 `merged` 重導用的是當下的 `tracks.json`,別台裝置只改 `tracks.json` 時我們的 `pl__` 是拿舊 tracks 算的(PR #30 review)。一次 list 涵蓋所有檔,不是每檔 GET 再 PATCH(那樣先傳的檔會在後面的檔檢查失敗後已經落地)。註:每次 COMMIT 都會 `manifest.Touch`,所以兩台裝置**任何**重疊的命令都會互相觸發守衛,即使動的是不同清單——預期行為,重跑就好;但守衛不依賴這個巧合。

殘餘的競態 = 上傳序列本身(tracks → pl__ → dev__ → manifest,秒級),文件明寫;Drive 沒有 CAS,這是能做到的上限。守衛對 `pl pull` / `resolve` / `push` / `sync` 一體適用(都走 `withCanonical`)。cron 下 exit 1 會被當失敗,那是對的:兩台裝置的 cron 若經常撞在一起,使用者該知道。

### 決策 30:Apple 寫入 gate 在 P0-2,fallback 是 append-only,不採 rebuild

Apple Music API 只文件化了 library 清單的建立(`POST /v1/me/library/playlists`)與新增曲目(`POST /v1/me/library/playlists/{id}/tracks`,body 帶 catalog `songs` id);移除、重排、改名、刪清單都沒有文件化端點。**P0-2 是寫入探測,只能由維護者在一個拋棄式 library 清單上跑**(§2 R-8 給步驟)。結果決定 T6:

- 移除 / 重排可行 → Apple 實作完整 `ApplyOps`。
- 不可行(預期)→ **append-only**:`add` 照做(append 到尾端,位置不保證),`remove` / `move` / `rename` 回 `ErrCapability`,push 列成 `manual`;base 仍以 L′ 前進,規則 4′ 讓那些「C 沒有、Apple 還有」的曲目不會回到 C,每次 push 會重複提醒直到使用者手動處理。
- **不採 v0.5 的 rebuild(建新清單 + 整批 + 改名 + 刪舊)**:刪清單同樣未驗證、清單 id 會變(link 要改)、Apple 端的封面 / 描述會丟、失敗中途會留下兩份清單。Q16 列著,建議不採。

ToS 灰色地帶(§8「內容不可與其他內容 synchronized」):push 只寫使用者自建的 library 清單,不碰 editorial;README 的揭露段要加 push。

### 決策 31:`pl sync` = 每個清單「先 pull 各平台、再 push 各平台」的一輪;`pl restore` 延後

`capy pl sync [name|pid] [--provider P] [--all] [--dry-run] [--yes] [--force]`:同一個 `withCanonical`、同一把鎖裡,對每個目標清單依 provider 字典序先 pull 全部、再 push 全部(`--provider` 只走那一個平台的一輪:Apple 還在 append-only 時「只 sync Spotify」是合理用法);變更集一次印完(pull 列與 push 列都帶 provider 欄)、確認一次、閾值對每個 (清單, provider) 各算。`--dry-run` 的 push 半邊是用「pull 套用後的 C」投影的,所以看得到完整一輪。**push 半邊的前提二重用 pull 半邊剛拿到的 L,不再打一次平台**(多一次 quota,還會讓「使用者剛好在這 200 ms 內動了清單」變成中途 exit 3、連 pull 半邊算好的變更一起丟);L′ 只在 ApplyOps 之後重讀。**sync 撞上版本守衛(決策 29)時平台已經改了、Drive 沒改**:exit 1 的訊息要講明,重跑一次 pull 半邊零變更(base 已在 L′)、push 半邊會把該補的補上。`pl restore`:base 是 per-device 的觀測快照,「從它回滾」等於「把上次看到的平台狀態 push 回去」,語意與 push 重疊,**延後到有人要為止**(Q18)。

### 決策 32:本 session 只產計畫與 spec 對齊(T0),等維護者 review 後再開 T1

與 P3 決策 12、P4 決策 25 同模式。特別因為決策 26 推翻了 v0.5 的 op log 設計。

## §3 任務切分(每個 task 一個 PR,PR 由維護者 review 後授權合併)

### T0 — 本計畫 + spec 對齊(docs only)

### T1 — SPI:`PlaylistWriter` + Spotify 實作
`provider.PlaylistOp{Kind add|remove|move|rename, ProviderID, Pos, From, Name}`,位置語意是**依序套用、每個位置指的是前面 ops 套完後的狀態**;`PlaylistWriter.ApplyOps(ctx, id, current []string, ops) error`(`current` = CLI 剛觀測到的 provider id 序列,ops 相對於它;provider 不再讀一次),不支援的 Kind 回 `ErrCapability`(呼叫端把那些列成 `manual`,其餘照做——所以實作要先把支援的做完再回 `ErrCapability`,或回一個帶「哪些沒做」的錯誤型別;T1 定)。Spotify:模擬 ops 於 `current` → `PUT /playlists/{id}/items`(≤100)+ `POST …?position=`(其後每批 100);`rename` → `PUT /playlists/{id}`;`Capabilities()` 加 `CapPlaylistAppend|Remove|Reorder`。**`PlaylistItems` 要先標 local file**:現況完全不看 `is_local`(local file 的 `id` 是 null、uri 是 `spotify:local:…`,ProviderID 會變成空字串),`provider.Track` 加 `Unpushable bool`(Apple 的 library-only 曲目同一個欄位),pull 的身分規則對它要有明確行為(Q22)。**T1 第一件事(需維護者授權,因為是寫入)**:對一個拋棄式 Spotify 清單各打一次 `PUT /playlists/{id}/items` 與 `/playlists/{id}/tracks`(帶目前的 uris,等於 no-op),確認寫入端點到底吃哪個路徑——讀取走 `/items` 是 P3 真帳號驗過的,寫入沒人驗過,文件上寫的是 `/tracks`,錯了是 404、fake 不會告訴你;同時釘住 `PUT` 空 `uris` 的語意(清空還是 400)——這是唯一一條一次刪光整個平台清單的路徑,閾值擋在前面但語意要明確。測試:fake 加 PUT / POST / rename 端點與 local file item,斷言分批邊界(0 / 1 / 100 / 101 / 250 首)、body 的 uri 格式、403 的友善訊息。**產出**:`internal/provider/provider.go`、`internal/provider/spotify/client.go`。

### T2 — 共享檔版本守衛(`withCanonical` COMMIT)
`commitCanonical` 上傳前再 `List` 一次,對 `s.fetched` 的**每個**檔(不只 staged)比對 `File.Version`,以及同名檔份數;不符 → 零上傳、exit 1。測試:fake Spotify 加 `onItems func()` 鉤子(OBSERVE 期間觸發),在 pull 的 FETCH 與 COMMIT 之間用 `putPlaylist` 模擬別台裝置寫 `pl__` → exit 1、上傳 0 次、本機 `state.db` 不變;重跑成功且包含對方的變更;**別台裝置只改 `tracks.json`、這次 pull 沒有要傳 tracks** → 仍然 exit 1(守衛不靠 manifest 的巧合);`resolve` 同樣受保護。加 `drivetest` 對 `version` 的斷言(已有 `version++`)。**產出**:`internal/cli/pull.go`(COMMIT)、`drive` 不動。

### T3 — 純函式:push 變更集(cid 對齊)、規則 4′ / 6′
`canon.PushPlan(live []LiveItem{CID, ProviderID, Unpushable}, want []Item, mappingID func(cid string) (string, bool)) (ops []provider.PlaylistOp, skipped []Skip)`——以 cid 對齊(LCS,重複照算),配不到的 want item 沒有可推的 id 就進 `skipped` 並從 want 拿掉;輸出 remove 依 live 位置由後往前、add 依 want 位置、move;位置語意同 T1;`Local` / library-only 的 live 項目配對後不動、配不到才 remove;DERIVE 規則 4′ 與 6′。測試:表格 + 隨機性質:(a) 任意 live / want,套用 PushPlan 的 ops 後等於 want(anchored 的留在原位);(b) 多平台 pull-push 序列的模型測試——兩個平台、兩台裝置、隨機在平台加 / 刪 / 換序,交錯 pull / push。**oracle 是意圖,不是收斂**:預期的最終狀態 = 初始狀態依序套上每一個平台操作(操作不衝突時),斷言 C 與每個平台的投影都等於它;「三方相等」本身不夠——重排被抵銷的那條軌跡三方也會相等(都錯成舊順序),復活也一樣。決策 27 的兩條反例(刪除被加回、重排被抵銷)各寫成固定測試;既有 3000 組單平台性質測試維持。**產出**:`internal/canon/project.go`、`derive.go`。
