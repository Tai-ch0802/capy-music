## §1 本次拍板的決策(2026-09-08;附錄 C 決策 26–32)

### 決策 26:不建 op log / HLC;同步模型 = per-device base + 三方語意的 DERIVE + 共享檔版本守衛

v0.5 的 op log(§6.4)是在「所有裝置寫同一份狀態」的前提下設計的:沒有 per-device base,就只能靠 ops 的全序(HLC)replay 出一致結果。P3 把 base 搬進 `dev__<device_id>.json` 之後,前提變了:

1. **每台裝置對每個平台都有自己的「上次對齊狀態」**,DERIVE 對最新的 C 算 delta 再套上去。兩台裝置各從不同平台 pull,只要 COMMIT 序列化,delta 自然疊加(A 先 commit C+ΔS,B FETCH 到它再疊 ΔA)。這就是三方合併,不需要 replay。
2. **沒有本機編輯命令,op log 沒有東西可記。** 每一筆 canonical 變更都是「觀測到平台跟 base 不同」,而觀測是可重做的(下次 pull 再算一次)。離線佇列也因此不存在:pull / push 都要 Drive,離線就是失敗、下次再跑。
3. 真正的洞不是缺 op log,是**共享檔的 lost update**:FETCH 到 COMMIT 之間別台裝置寫了 `pl__`,我方 COMMIT 蓋掉、而我方 `dev__` 的 base 已前進 → 對方 derive 出來的變更永遠不會再被 derive(base 對得上平台、C 卻少了)。這用版本守衛擋(決策 29),不用 op log。

**代價(要讀清楚):**
- **沒有 base 的裝置會復活別台裝置刪掉的歌**:X 在 Spotify 被刪、裝置 A pull 後 C 沒有 X、但還沒 push 到 Apple;裝置 B(新裝置,或第一次 pull 剛連結的 Apple)pull Apple 時沒有 `base_Apple`,規則 4 的 bootstrap 語意把 L 全部當新增 → X 回到 C。窗口 = 「A 端刪除已 pull、尚未 push 到 B 平台、B 裝置對 B 平台無 base」三者同時成立;任何一台裝置跑一次 `pl sync` 就關掉窗口,而且復活會以 `add` 列出現在 B 裝置的 pull 輸出(`--dry-run` 看得到)。**Q15:接受並文件化(建議),或給 `pl__` 加 item 級 tombstone(`removed{cid: ts}`、30 天過期)。** 這是 v0.5「tombstone 必須保留」那句話在新模型裡唯一還沒被規則 4′ 涵蓋的情境。
- `rename` 與 rank 衝突沒有 HLC 可比:兩台裝置對同一清單分別從兩個平台 pull 到不同名字 → 後 COMMIT 者勝(規則 7 是「平台名 ≠ base 名才改」,所以只有兩邊真的都改了名才會互蓋),版本守衛保證後者看得到前者的結果再決定。順序同理:以最後一次 pull 的平台為準(§6.5.1 規則 6 原文)。
- 如果將來加 `pl add/remove/move`:它們直接改 C、走同一個 `withCanonical`(FETCH → 改 → 版本守衛 → COMMIT),仍然不需要 op log;離線編輯要佇列時才回頭看 §7 的重建策略。

### 決策 27:DERIVE 規則 4 改為 base-aware(三方語意),與規則 5 對稱

現況:規則 5(移除)只在 base 存在時發生、上限 b − l;規則 4(新增)**不看 base**,L 裡配不到 C 的出現一律 add。單平台時沒差;雙平台時:使用者在 Spotify 刪了 X → Spotify pull 從 C 移除 X → Apple pull 看到 L 有 X、C 沒有 → **把 X 加回來**。push 到 Apple 時就沒有東西可刪,刪除意圖丟失;`pl sync` 的結果甚至取決於先 pull 哪個平台。這正是 v0.5 寫 tombstone 要擋的情境。

新規則 4′:base 存在時,cid X 在 L 裡配不到 C 的出現,**只有超出 base 計數的部分才是新增**——l(X) − b(X) > 0 才 add,至多 add 這麼多個,取 L 順序最後的那幾個(平台新增通常在尾端;鏡像規則 5「依 rank 由後往前移除」);其餘配不到的出現是「平台還沒跟上 C 的移除」,留給 push 去刪。沒有 base 時全部 add(bootstrap,不變)。

**這是改 DERIVE 語意的 PR,必須跟 push 一起出**(T3 + T4 相鄰):只有 pull 的世界裡,規則 4′ 會讓 C 跟平台脫節而沒有東西去對齊。T2b 說過「T2b 是唯一改 DERIVE 的 PR」,P5 T3 是第二個,理由寫在這裡。3000 組隨機性質測試要擴成多平台 / 多裝置的 pull-push 序列(§3 T3)。

### 決策 28:`pl push` 的契約(附錄 A)

`capy pl push [name|pid] [--provider P] [--all] [--dry-run] [--yes] [--force]`,形狀與 exit code 完全鏡像 `pl pull`(0 無變更 / 已套用、1 錯誤、2 待套用、3 安全閥)。對每個目標 (清單, provider):

1. **前提一:base 存在**(本裝置對這個平台清單 pull 過)。沒有 → exit 3、零寫入,訊息「先 `capy pl pull`」。不然 diff(L, project(C)) 會把平台上所有不在 C 的曲目刪光——這是「首次 pull 永不移除」的 push 版。
2. **前提二:平台沒有未 pull 的變更**:先跑一次 Derive(base, L),變更集非空 → exit 3,訊息「平台有未 pull 的變更,先 `capy pl pull`(或用 `pl sync`)」。push 蓋掉使用者剛在平台改的東西是不可接受的。`pl sync` 先 pull 後 push,兩個前提由建構保證。
3. **投影**:project(C, P) = C 的 items 依 rank,每個取 `tracks[cid].mappings[P].id`;pinned 不可得或沒有 mapping → 跳過並列成 `skip` 列(reason 指向 `capy resolve`),不阻擋其他曲目;Apple 只接受 catalog id,library id(`i.` 開頭)也跳過(Q17)。
4. **變更集**:diff(L 的 provider id 序列, 投影)以 LCS 配對(重複照算,與 §6.5.1 規則 2 同一套)→ `remove`(L 位置)、`add`(投影位置)、`move`、`rename`(C.name ≠ L.name 且 provider 支援改名),TSV 欄位與 pull 一樣 `action pos cid provider_id title artists reason`,再加 `skip`。
5. **安全網**:`remove` 數過決策 18 的閾值(分母 = L 的長度),超過 → exit 3、`--force` 才越過且只能配單一清單;`--dry-run` 只印、exit 2(有變更)/ 0,不碰平台也不碰 Drive;非 TTY 沒 `--yes` → exit 2;TTY 確認。
6. **套用**:`provider.ApplyOps(ctx, id, ops)`(T1);provider 對某類 op 回 `ErrCapability`(Apple 的 remove / move)→ 那些列標成 `manual`(「Apple 端請手動」),其餘照做。
7. **驗證與前進 base**:套用後**重讀 L′**,L′ ≠ 投影(平台拒收某首、順序被平台正規化)→ stderr 警告但不視為錯誤;base[pid][P] := L′ 的快照(id 原文 + 觀測當時的 cid,與 pull 同一個 Observe 路徑,所以順便補 mapping / conflicts);C 不變(push 不改 canonical)。
8. **COMMIT**:走 `withCanonical` 同一套(版本守衛 → tracks → pl__ → dev__ → manifest → SQLite)。平台已改、Drive 上傳失敗 → base 沒前進,下次 pull 會把我們剛 push 的東西當「平台變更」再 derive 一次:LCS 對同 cid 會配上、零變更,**不會重複**(這正是 base-aware 規則的好處),訊息照 pull 的「本機快取未動,下次 pull 重算」。

**Spotify 的套用策略**:任何 add / remove / move → 整批取代:`PUT /playlists/{id}/items`(前 100 首)+ `POST /playlists/{id}/items?position=`(其後每 100 首一批);`rename` → `PUT /playlists/{id}`。取代會丟掉 Spotify 端每首的 `added_at` / `added_by`(Q19;升級路徑是逐條 DELETE / POST / PUT range 的最小操作,並帶 `snapshot_id` 做樂觀鎖)。只有使用者自己或協作的清單可寫,403 → 友善訊息。

### 決策 29:共享檔版本守衛(lost update 變成可偵測、可重跑)

COMMIT 前**再跑一次 FETCH 用的 `files.list`**(fields 已含 `version`),對每個要上傳的檔比對 FETCH 時記下的 `File.Version`;任一不同、或同名檔多了一份(別台裝置在我們 FETCH 之後 Create 的)→ **一個檔都不傳**、本機不動、exit 1,訊息「Drive 上的 X 在這次執行期間被別台裝置改過;重跑一次」。一次 list 涵蓋所有檔,不是每檔 GET 再 PATCH(那樣先傳的檔會在後面的檔檢查失敗後已經落地)。

殘餘的競態 = 上傳序列本身(tracks → pl__ → dev__ → manifest,秒級),文件明寫;Drive 沒有 CAS,這是能做到的上限。守衛對 `pl pull` / `resolve` / `push` / `sync` 一體適用(都走 `withCanonical`)。cron 下 exit 1 會被當失敗,那是對的:兩台裝置的 cron 若經常撞在一起,使用者該知道。

### 決策 30:Apple 寫入 gate 在 P0-2,fallback 是 append-only,不採 rebuild

Apple Music API 只文件化了 library 清單的建立(`POST /v1/me/library/playlists`)與新增曲目(`POST /v1/me/library/playlists/{id}/tracks`,body 帶 catalog `songs` id);移除、重排、改名、刪清單都沒有文件化端點。**P0-2 是寫入探測,只能由維護者在一個拋棄式 library 清單上跑**(§2 R-8 給步驟)。結果決定 T6:

- 移除 / 重排可行 → Apple 實作完整 `ApplyOps`。
- 不可行(預期)→ **append-only**:`add` 照做(append 到尾端,位置不保證),`remove` / `move` / `rename` 回 `ErrCapability`,push 列成 `manual`;base 仍以 L′ 前進,規則 4′ 讓那些「C 沒有、Apple 還有」的曲目不會回到 C,每次 push 會重複提醒直到使用者手動處理。
- **不採 v0.5 的 rebuild(建新清單 + 整批 + 改名 + 刪舊)**:刪清單同樣未驗證、清單 id 會變(link 要改)、Apple 端的封面 / 描述會丟、失敗中途會留下兩份清單。Q16 列著,建議不採。

ToS 灰色地帶(§8「內容不可與其他內容 synchronized」):push 只寫使用者自建的 library 清單,不碰 editorial;README 的揭露段要加 push。

### 決策 31:`pl sync` = 每個清單「先 pull 各平台、再 push 各平台」的一輪;`pl restore` 延後

`capy pl sync [name|pid] [--all] [--dry-run] [--yes] [--force]`:同一個 `withCanonical`、同一把鎖裡,對每個目標清單依 provider 字典序先 pull 全部、再 push 全部;變更集一次印完(pull 列與 push 列都帶 provider 欄)、確認一次、閾值對每個 (清單, provider) 各算。`--dry-run` 的 push 半邊是用「pull 套用後的 C」投影的,所以看得到完整一輪。`pl restore`:base 是 per-device 的觀測快照,「從它回滾」等於「把上次看到的平台狀態 push 回去」,語意與 push 重疊,**延後到有人要為止**(Q18)。

## §3 任務切分(每個 task 一個 PR,PR 由維護者 review 後授權合併)

### T0 — 本計畫 + spec 對齊(docs only)
spec §6.3(共享檔取捨 → 版本守衛;op log 段落刪)、§6.4 改寫成新模型、§6.5 的一輪流程重畫、§6.5.1 規則 4′、新增 §6.5.2 push 規則、§6.6 加前提與守衛列、§7 P5 不加表、§9 P5 條目、附錄 A 三條命令、附錄 C 決策 26–32、§3 SPI 的 `PlaylistOp` 形狀。**PR 描述要講明「P5 不建 op log」是設計轉向。**

### T1 — SPI:`PlaylistWriter` + Spotify 實作
`provider.PlaylistOp{Kind add|remove|move|rename, ProviderID, Pos, From, Name}`,位置語意是**依序套用、每個位置指的是前面 ops 套完後的狀態**;`PlaylistWriter.ApplyOps(ctx, id, ops) error`,不支援的 Kind 回 `ErrCapability`(呼叫端把那些列成 `manual`,其餘照做——所以實作要先把支援的做完再回 `ErrCapability`,或回一個帶「哪些沒做」的錯誤型別;T1 定)。Spotify:模擬 ops 於 `PlaylistItems` 取回的現況 → `PUT /playlists/{id}/items`(≤100)+ `POST …?position=`(其後每批 100);`rename` → `PUT /playlists/{id}`;`Capabilities()` 加 `CapPlaylistAppend|Remove|Reorder`。測試:fake 加 PUT / POST / rename 端點,斷言分批邊界(0 / 1 / 100 / 101 / 250 首)、body 的 uri 格式、403 的友善訊息。**產出**:`internal/provider/provider.go`、`internal/provider/spotify/client.go`。

### T2 — 共享檔版本守衛(`withCanonical` COMMIT)
`commitCanonical` 上傳前再 `List` 一次,對 staged 的每個檔比對 `fetched[name].file.Version`,以及同名檔份數;不符 → 零上傳、exit 1。測試:fake Spotify 加 `onItems func()` 鉤子(OBSERVE 期間觸發),在 pull 的 FETCH 與 COMMIT 之間用 `putPlaylist` 模擬別台裝置寫 `pl__` → exit 1、上傳 0 次、本機 `state.db` 不變;重跑成功且包含對方的變更;`resolve` 同樣受保護(tracks.json 被改)。加 `drivetest` 對 `version` 的斷言(已有 `version++`)。**產出**:`internal/cli/pull.go`(COMMIT)、`drive` 不動。

### T3 — 純函式:投影、push 變更集、規則 4′
`canon.Project(pl, tracks, prov) (ids, cids []string, skipped []Skip)`;`canon.PushPlan(live, want []string) []provider.PlaylistOp`(LCS 配對重複照算;輸出 remove 依 live 位置由後往前、add 依 want 位置、move;位置語意同 T1);DERIVE 規則 4′。測試:表格 + 隨機性質:(a) 任意 live / want,套用 PushPlan 的 ops 後等於 want;(b) 多平台 pull-push 序列的模型測試——兩個平台、兩台裝置、隨機在平台加 / 刪 / 換序,交錯 pull / push,斷言「某平台刪掉的 cid 在另一平台 push 後也消失」與「全部 sync 兩輪後三方(C、L₁、L₂ 的投影)相等」;既有 3000 組單平台性質測試維持。**產出**:`internal/canon/project.go`、`derive.go`。

### T4 — `capy pl push`
決策 28 的每一條;`observeAndDerive` 拆出可重用的 OBSERVE(L 取回 + 身分算 cid + Observe 寫 tracks)給 push 的前提二與 L′ 重讀共用;TSV 表頭沿用 `pullHeader`;stderr 提示「N 首沒有 P 的 mapping,跑 capy resolve」;Apple 在 T6 前一律「尚不支援寫入(P0-2)」。e2e:fake Spotify 記錄 PUT / POST 的內容;首次 push 無 base → exit 3;平台有未 pull 變更 → exit 3;閾值;dry-run 零寫入(平台與 Drive);push 後再 pull 零變更;Drive 上傳失敗後的 pull 不重複(R-7 的注入版);刪 db 重建等價。README:push 段落 + 揭露段加 push。
